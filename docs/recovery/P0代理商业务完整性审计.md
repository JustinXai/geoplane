# P0 代理商业务完整性审计

结论：**PASS_WITH_CHANGES**。复审对象为 `59c1545`。

## 已完成的业务合同

- 工作流包含客户档案、项目档案、企业知识、账号授权、百度关键词、AI 扩展、用户问题确认、内容任务、内容审核、国内 AI Probe、报告、交付和复盘。
- 状态转换为显式白名单；每次转换要求 actor 与 reason，0015 以只追加事件保存。
- `MARK_READY` 要求报告阶段完成；`REGISTER_DELIVERED` 要求先 READY 且必须提供人工回执引用。
- 读模型已从 PostgreSQL 读取授权客户、项目、知识、关键词审核、内容、账号和交付事实；没有 Fixture 注入，但部分未接事实仍被写成 0，见下方缺口。
- 代理商只能请求自身组织；平台管理员可读取平台代理商聚合。服务层写操作再次调用客户授权 Port。
- 没有计费、佣金、订阅、白标或自动发布状态。

## 已关闭的原阻断

`PgAgencyClientAuthorizationPort`、`PgAgencyDeliveryReadPort`、`PgAgencyDeliveryWritePort` 已实现，运行时可由 `GEO_DATABASE_URL` 生产组合，不再依赖测试注入。

## 剩余完整性缺口

1. `workflow`/`deliveries` 路由没有验证 body client 是项目真实所有者；服务只验证 agency-client 授权，无法阻止同一代理商两个授权客户之间的 project/client 错配。
2. PG Read Model 将 `probeTaskCount`、`failedProbeCount`、`rejectedContentCount` 固定为 0；这不是数据库事实。
3. `passedContentCount` 直接等于全部 approval，缺少明确口径；待交付查询只要项目存在任一 Delivery 就排除该项目全部 PublishPackage，可能漏报。
4. 新测试使用 SQL fake，尚未证明真实 PostgreSQL schema、正式路由、刷新连续性和跨租户行为。

## 修复验收门槛

- 在路由、服务和数据库三层验证 project/client/agency ACTIVE assignment 一致。
- 从真实 Probe/审核事实查询指标；无法计算时返回明确不可用，不得补 0。
- 待交付状态按 PublishPackage -> DistributionPlan -> Delivery/Receipt 的具体关系计算。
- 增加三角色真实 PostgreSQL 路由测试：未登录 401、非代理商 403、未授权客户 403、授权客户可读写、刷新后连续、跨租户零泄漏。
- 验证人工回执写入后可从真实 Read Model 读取，并确认没有自动发布或自动交付路径。

在上述门槛通过前，代理商能力只能标记为 `PARTIAL_RUNTIME`，仍阻断 P0 完成判定。
